# `/src` — локальный сервис просмотра координационной базы (бэкенд)

**Черновик.** ASP.NET Core minimal API поверх `mezosync.db`. Открывает базу **только на чтение**,
периодически перечитывает и отдаёт JSON. Интерфейс живёт отдельно — в соседней папке
[`/srcclient`](../srcclient/README.md).

## ⛔ Чего этот сервис НЕ делает

- **Не пишет в базу.** Ни строки, ни DDL, ни `PRAGMA`, меняющих файл. Три независимых замка:
  `Mode=ReadOnly` при открытии · `PRAGMA query_only = 1` на соединении · весь SQL — только
  `SELECT`/`PRAGMA`, собран в одном файле `Data/MezosyncReader.cs`.
- **Не слушает сеть.** Только `127.0.0.1`. Аутентификации нет вовсе, поэтому наружу нельзя:
  порт меняется (`--port`), адрес — нет.
- **Не открывает произвольные файлы по запросу из браузера.** Переключиться можно только
  на базы, найденные под корнем обхода, который задал человек при запуске.
- **Не пул соединений.** Живое читающее соединение к базе в режиме WAL мешало бы пишущей
  стороне усекать журнал — то есть просмотрщик влиял бы на работу контура.

## Запуск

```bash
# одна конкретная база
dotnet run --project src/Gordi.Viewer.Api -- --db C:/путь/к/mezosync.db

# каталог: сервис найдёт в нём *.db и даст выбрать в интерфейсе
dotnet run --project src/Gordi.Viewer.Api -- --dir C:/путь/к/каталогу

# порт и период обновления
dotnet run --project src/Gordi.Viewer.Api -- --db ... --port 5177 --refresh 10
```

Проверка, что поднялся: <http://127.0.0.1:5177/api/health>.

### Откуда берётся путь к базе

Три источника, приоритет снизу вверх (побеждает последний):

| Источник | Пример | Когда удобен |
|---|---|---|
| `appsettings.json`, секция `Viewer` | `"Db": "C:/.../mezosync.db"` | «моя обычная база», открываю каждый день |
| переменные среды | `GORDI_DB`, `GORDI_DIR`, `GORDI_PORT`, `GORDI_REFRESH_SECONDS` | ярлык или скрипт запуска |
| аргументы запуска | `--db`, `--dir`, `--port`, `--refresh` | разовый запуск над чужой базой |

Своего разбора командной строки нет: всё это уже умеет сам ASP.NET Core, добавлено только
отображение читаемых имён (`--db`) на канонические ключи (`Viewer:Db`).

## Что отдаёт

| Метод | Что | Откуда данные |
|---|---|---|
| `GET /api/health` | жив ли, какая база, когда перечитывал, последняя ошибка | память |
| `GET /api/sources` | найденные базы под корнем обхода | файловая система |
| `POST /api/sources/select` | переключить активную базу (`{"path": "..."}`) | — |
| `POST /api/refresh` | перечитать немедленно | база |
| `GET /api/overview` | счётчики + версия схемы | снимок |
| `GET /api/tasks?status=&role=&missingCriterion=` | карточки задач | снимок |
| `GET /api/tasks/{id}` | карточка + события + проверки + связанные записки | база |
| `GET /api/messages?limit=&offset=&role=&priority=&search=` | лента страницами | база |
| `GET /api/messages/{id}` | тело записки целиком | база |
| `GET /api/writers` | список авторов для фильтра | база |
| `GET /api/roles` | роли: состояние, курсор, память, активность | снимок |
| `GET /api/rules` | правила | снимок |
| `GET /api/schema` | что в базе есть и чем она отличается от эталона | снимок |

### Почему лента НЕ в снимке

Снимок (обзор, задачи, роли, правила, схема) пересобирается фоново по таймеру — это сотни строк,
дёшево. Лента — нет: замер живой базы 2026-08-06 16:39 UTC дал 3028 записок, суммарно ≈ 5.25 МБ
тел, самое длинное 10 938 символов. Держать это в памяти ради страницы из 50 строк незачем, поэтому
лента читается запросом (тоже только на чтение), с ограничением размера страницы.

Дата у числа стоит не для порядка: база живая. За двадцать минут между двумя замерами в ней
прибавилось 7 записок, две карточки задач переехали в «закрыто», и появились два новых
представления. Порядок величины держится, точное значение — нет.

## Как он держится за схему, которая меняется

Живая база и эталон `vnext/prototype/schema_vnext.sql` **расходятся** — это замер, а не
предположение (2026-08-06): часть таблиц эталона отсутствует, часть живых таблиц эталон не знает,
а у совпадающих отличается состав колонок. Поэтому сервис **спрашивает базу, а не помнит**:
`SchemaProbe` читает `sqlite_master` и `PRAGMA table_info`, а каждый запрос сначала проверяет,
есть ли из чего читать.

Главное следствие — правило честности, встроенное в тип `Measure`:

> **Отсутствие поля — это не ноль.** Если в базе нет колонки `backlog.done_when`, ответ будет
> «в этой базе критерий приёмки не хранится», а не «задач без критерия: 0». Ноль читался бы как
> хорошая новость и был бы ложью.

То же правило действует на страницах интерфейса: пустой столбец подписан «данных негде хранить»,
а не оставлен пустым молча.

## Сборка

```bash
dotnet build src/Gordi.Viewer.Api
```

Зависимости — `Microsoft.Data.Sqlite.Core` + `SQLitePCLRaw.bundle_e_sqlite3` (а не мета-пакет
`Microsoft.Data.Sqlite`): именно эта пара нашлась в локальном кэше NuGet, то есть восстановление
проходит без обращения к сети.

⚠️ **Известное предупреждение:** `NU1903` — у `SQLitePCLRaw.lib.e_sqlite3` 2.1.11 есть
зарегистрированная уязвимость (GHSA-2m69-gcr7-jv3q). Закрывающая версия существует
(`SQLitePCLRaw.bundle_e_sqlite3` 3.0.5 + `Microsoft.Data.Sqlite.Core` 10.0.10 — с ними сборка
проходит вообще без предупреждений, проверено). В черновике оставлена 2.1.11, потому что 3.x —
мажорный скачок сверх того, что объявляет зависимостью сам `Microsoft.Data.Sqlite`, а проверить
поведение в рантайме без запуска сервиса нельзя. Решение о переходе — за владельцем.

## Чем это отличается от `viewer/index.html`

Тот просмотрщик — одна страница на `sql.js`: файл базы выбирается руками, целиком грузится
в память браузера, «обновить» = перечитать файл заново. Он самодостаточен и работает офлайн
без всякого сервера — и этим ценен.

Здесь другое: сервис живёт рядом с базой, перечитывает её сам по таймеру, знает про расхождение
схем и отвечает на вопросы, ради которых всё затевалось, — прежде всего «какие задачи открыты
и у каких из них НЕТ критерия приёмки». Один другого не отменяет.
