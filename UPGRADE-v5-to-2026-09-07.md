## 1. Что появляется — одним замыслом: роль перестаёт читать свою память целиком

Замер 2026-09-04 13:25 UTC: роль читала за пробуждение 66–124 тыс. знаков (семь разделов),
порог 20 000 стоял на разделе, потолок по факту — 140 000 на роль. К 07.09 полное чтение
памяти COORD — 92–95 тыс. знаков; ответ поиска по словам — в среднем около 1 тыс. знаков
(экономия 98,9 %, ожидаемая запись первой у 5 запросов из 10, ещё одна в тексте раздела
и одна в архиве). Числа — на памяти COORD, самой большой в контуре; у других доля иная.

- **Архив памяти роли отдельной таблицей** (`phoenix_archive`, шаг 20260904-phoenix-archive):
  старые куски раздела уносятся переносом, не удалением; инструмент `memory-archive.py`
  (`--preview`, перенос, `--find`). Подсказка о превышении порога печатает полный путь.
- **Память записями с полями** (`phoenix_records`, шаги 20260904-phoenix-records и
  …-autoincrement): раздел режется на записи с предметом, датой, источником, условием
  снятия и живостью; номер держится за телом и не переиспользуется. Инструмент
  `memory-records.py` (`--разобрать`, `--пересобрать`, `--отобрать`, `--снять`, `--собрать`).
- **Автопересборка записей** при каждом сохранении памяти: `save-phoenix.py` после строки
  «OK» пересобирает записи раздела и печатает «🧩 записи раздела: сохранили номер N ·
  новых K · удалено D»; отказ слоя — предупреждением, сохранение не откатывается.
- **Полнотекстовый поиск по записям** (`phoenix_records_fts`, движок FTS5 + три триггера,
  шаг 20260907-phoenix-records-fts) и инструмент `find-phoenix.py`: три уровня (записи →
  текст раздела → архив), исходы кодами возврата 0 найдено · 2 нет нигде (+ «может быть»)
  · 3 есть в тексте раздела (записи отстают либо слова разбросаны) · 4 только в архиве ·
  5 нет индекса; повтор по началу слов; ступень «часть слов» от трёх слов в запросе;
  снятые записи с пометкой; регистр сворачивается. Форма:
  `python <КОНТУР>/.mezosync/scripts/find-phoenix.py --role COORD --actor COORD "слова запроса"`.

- **История версий памяти — в архив, не под нож** (`phoenix_history_archive` +
  `role_rebirths`, шаг 20260905-phoenix-history-archive): чистка истории переносит
  версии; отметки пересоздания роли — `rebirth-mark.py` (Шаг 0-бис промпта нового чата).
- **Отказ сохранения на служебных блоках читалки**: тело памяти не примет снимок
  открытых карточек/положения в ленте, который печатает читалка.

## 2. Перед началом — два обязательных условия

1. Бэкап, проверенный **разворачиванием**: копия через SQLite backup API (файловая копия
   при живых писателях в WAL-режиме даёт рваный снимок), `SELECT * FROM schema_version`
   на копии обязан ответить `v5`, а `SELECT count(*) FROM schema_migrations` — числу
   шагов вашего журнала (у эталона перед этой серией — 25).
2. Сборка SQLite с FTS5: `python -c "import sqlite3;print(sqlite3.sqlite_version)"` и
   `SELECT sqlite_compileoption_used('ENABLE_FTS5')` → 1. Без FTS5 шаг поиска откажет
   словами, остальное накатывается.

## 3. Как обновиться

Инструменты — потребитель забирает пакет `scripts/` штатно:
```
python <КОНТУР>/.mezosync/scripts/update-tools.py            # план: что изменится
python <КОНТУР>/.mezosync/scripts/update-tools.py --apply    # запись; файлы со своей правкой — не трогает без --overwrite-unknown
```
Схема — 11 шагов и веха накатываются **в этом порядке** (порядок — по журналу эталона),
каждый сперва `--dry-run`, затем без него; каждый идемпотентен (повтор отвечает «уже
сведено»), обрыв лечится повтором:
```
migrations/20260830-backlog-reviewer.py
migrations/20260830-lease-waits.py
migrations/20260904-rule-skill-delivery.py
migrations/20260904-phoenix-archive.py
migrations/20260904-phoenix-records.py
migrations/20260904-phoenix-records-autoincrement.py
migrations/20260905-phoenix-history-archive.py
migrations/20260905-messages-archive.py
migrations/20260905-role-sessions.py
migrations/20260907-hint-seen.py
migrations/20260907-phoenix-records-fts.py
migrations/20260907-milestone-v6.py          # веха: ПОСЛЕДНЕЙ; сверяет НАБОР 11 шагов поимённо
```
Веха отказывает, если под ней не хватает шага, и называет его по имени; при отказе —
прогнать недостающий шаг и повторить веху. После неё `SELECT * FROM schema_version`
отвечает `v6 · шагов N · сверх отметки 0`.
Автор шага берётся из окружения `MEZO_ROLE`; путь к базе — доводом `--db` (необязателен:
резолвится от расположения скрипта).

После схемы:
- **Первый разбор записей** у каждой роли случится сам при её ближайшем сохранении памяти
  (строка «🧩 записи раздела: разобрано N записей (первый разбор)»); раньше — рукой:
  `python <КОНТУР>/vnext-tools/memory-records.py --role <РОЛЬ> --section <РАЗДЕЛ> --разобрать`.
- **Подсказки ролей** пересобрать генератором из свода (`rules-to-skills.py --write`) и
  прогнать проверку свежести — правка свода без пересборки оставляет роли старую редакцию
  (оплачено 07.09 16:01–16:36 UTC).
- **Реестр адресов**: каждая роль записывает свой адрес сама
  (`signal-templates.py --role <РОЛЬ> --set-address "…"`), запись живёт сутки.
