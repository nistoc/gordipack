## Зачем этот выпуск

Проверку писем соседей переделывали четыре раза (карточки #221, #242, #665, #673). Причина каждый раз одна:
автора, адресата и связь «ответ — вопрос» проверка угадывала по имени файла и первой строке письма. Второе
слово имени значило то автора, то адресата; ответ связывался с вопросом по совпадению темы, и ответ на
«roles-core» засчитывался вопросу «roles»; письмо соседа, положенное в нашу папку, по папке считалось нашим.

С этого выпуска письмо несёт **шапку с полями**, и проверка читает поля. Письмо без шапки судится прежними
правилами — старые письма не трогаются и не судятся заново (решение Р5 карточки #681).

## 1. Шапка письма

```
2026-10-13 09:30 UTC · пишет PROTO контура atlas, адресат — COORD@onto
---
id: atlas:atlas-onto/answer.onto.e4-update-doc.20261013-0930
from: PROTO@atlas
to: COORD@onto
reply-to: onto:atlas-onto/2026-10-05-to-proto-e3-step0-stop
kind: answer
---

<текст письма>
```

| поле | значение | обязательно |
|---|---|---|
| `id` | `<контур-владелец папки>:<папка>/<имя файла без .md>` — одна форма для старых и новых писем | да |
| `from` | `<РОЛЬ>@<контур>` автора; роль — латинские буквы, цифры, «-» и «_», может начинаться с цифры (`9P@dominal`) | да |
| `to` | одна или несколько `<РОЛЬ>@<контур>` через запятую; `all@<контур>` — всем ролям контура | да |
| `reply-to` | `id` письма, на которое это ответ | у `answer` и `fix` |
| `kind` | `ask` (ждёт ответа) · `answer` · `status` (ответа не ждёт) · `fix` (поправка к СВОЕМУ письму) | да |
| `due` | `ГГГГ-ММ-ДД` — до какой даты ждут ответа | только у `ask`, по желанию |

```
где блок ............ ВТОРЫМ, после первой строки для человека. Разбор ищет его в первых трёх непустых строках.
                      Блок первым шапкой остаётся, но проверка предупреждает: прежний разбор у соседа, ещё не
                      обновлённого, читает первую строку и теряет автора и адресата
первая строка ....... «<дата время> UTC · пишет <РОЛЬ> контура <мы>, адресат — <РОЛЬ>@<контур>».
                      ⚠️ НЕ «адресат — COORD контура onto»: прежняя проверка у соседа ищет «контура <его имя>»
                      в первой строке и сочла бы ваше письмо СВОИМ — оно ушло бы из-под её разбора
имя файла ........... <kind>.<контур-адресат>.<тема>.<ГГГГММДД-ЧЧММ>.md — метка времени даёт уникальность:
                      второй ответ на тот же вопрос не стирает первый
черта «---» ......... шапкой считается, только если первая строка за чертой — поле из таблицы; иначе это
                      обычная черта markdown
```

## 2. Что изменилось

```
new-bridge-letter.py .... НОВЫЙ инструмент письма: ставит шапку и первую строку, кладёт письмо в исходящую
                          папку соседу (сначала «<мы>-<он>», иначе единственная папка с обоими именами, иначе
                          отказ с перечнем; --box — назвать папку самому). Отказывает: нет обязательных флагов ·
                          все адресаты — свой контур · answer/fix без --reply-to · fix не к своему письму ·
                          due не у ask или не ГГГГ-ММ-ДД · в тексте уже есть шапка · файл с таким именем есть.
                          reply-to, которого не нашлось ни в наших папках, ни у соседей, — предупреждение.
                          --check <файл> — проверить шапку готового письма: код 0 годна · 1 негодна · 2 шапки нет
bridge_letter.py ........ НОВЫЙ: разбор шапки — одно место; его зовут guard-all.py, sync_backoff.py и инструмент
guard-all.py ............ письмо с годной шапкой судится по полям: своё — from = наш контур; вопрос нам —
                          kind ask и наш контур в to; отвечен — есть письмо с reply-to = id вопроса в любой папке
                          пары (несколько ответов называются все). Ответы с полями в сличение по теме не входят.
                          Новая строка «📨 мост: писем с полями (Э7) — годных N (наших K) · шапка негодна — M ·

                          предупреждениями. Предупреждения «⚠️»: шапка негодна (с причиной; письмо судится

                          шапкой)
sync_backoff.py ......... чтение ленты: письмо с годной шапкой — сосед из from, адресаты из to; своё письмо в
                          общей папке новостью не считается; письмо третьему контуру — «контур X», не «тебе»
```

## 5. Как писать соседу после обновления

- Новое письмо — инструментом `new-bridge-letter.py`: он ставит поля сам. Письмо, написанное руками, проверьте
  `new-bridge-letter.py --check <файл>`.
- Ответ — `--kind answer --reply-to <id вопроса>`. `id` вопроса — из его шапки; у старого письма без шапки —
  по форме из раздела 1: `<контур-владелец папки>:<папка>/<имя без .md>`.
- После вашего первого письма с полями у обновившихся соседей ваше письмо без полей получает предупреждение.
- Приёмка этапа у соседа (решение Р7 «а» владельца, 09.10 14:02 UTC): контур обновился до этого выпуска без
  ручного сведения, и его первое письмо после обновления — с шапкой, а проверка эталона судит его по полям верно.

## 7. Известно и в этом выпуске НЕ сделано

- Старые письма (у эталона 429) не правятся и шапки не получают (решение Р5).
- «Отвечен по полю reply-to» значит, что ответ связан с вопросом, а не что он полон по существу. Это проверка
  не знает и пишет об этом строкой «⚖️» под каждым таким вопросом (с `--full`).
- Прогон `bite-all.py --target` по копии пакета у части приёмок по-прежнему испытывает инструменты живого
  контура: они берут каталог инструментов от расположения контура, а не от запускающего. Исправлены две
  приёмки моста; остальные — карточка #682.
- Письма соседям о новом формате эталон не рассылал — это решает владелец эталона.
- Роль с цифрой первой (`9P`) читается из полей шапки. В письме БЕЗ шапки прежний разбор адресатов чтения ленты
  (`sync_backoff.py`, признак «@РОЛЬ» и имя роли в первых строках) такую роль не узнаёт, как и до выпуска: прежние
  правила этот выпуск не меняет (решение Р5).
