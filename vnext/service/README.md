Этап **Э1** переделки тулинга (слово владельца 2026-11-15 01:17 UTC, чат PROTO;
план — `atlas.archs/.mezosync/goal-gordipack-vnext/00-README.md`, дизайн — `01-DESIGN.md`,
оценка предложения о выносе за стену — `02-MCP-EVALUATION.md`, критерий приёмки — карточка 779).

Стена **не переписывает** прежние инструменты. Она становится **единственным общим входом к ним**:
роль больше не зовёт файлы напрямую, а просит вызов по имени и получает ответ,
у которого исход назван словом из закрытого перечня, а усечение — отдельным признаком.

## Что это лечит

| Класс из разбора 121 незакрытой карточки | Чем лечит стена |
|---|---|
| договор вызова живёт в голове роли (24 карточки) | договор — ОДИН файл, из него и служба, и справка, и перечень |
| код выхода беднее исходов инструмента (21) | типизированный исход + отдельный признак усечения; код тела — справочно |
| чаты правят инструменты напрямую (13) | тела за стеной; роль их не зовёт и не правит |
| инструмент считает путь контура сам (10) | контур приходит **в вызове**, среда ребёнка чистится от `MEZO_*` |
| обрыв текста неотличим от конца (2) | длинный вывод выдаётся частями, а не режется; `truncated` — только для настоящего отсечения; молча обрезать нельзя |
| кодировки | ребёнок всегда в UTF-8 (`PYTHONUTF8`), длинный текст идёт файлом, а не аргументом |

## Четыре режима одной сборки

```
gordi-wall serve --contours <манифест>     # служба MCP по стандартному вводу-выводу (так её зовут роли)
gordi-wall run <вызов> --contour <имя> …   # однократный вызов МИМО службы, ТОЛЬКО чтение
gordi-wall run <вызов> --contour <имя> --json   # то же, но вместо текста ОДИН документ JSON (см. «Ответ одним документом JSON»)
gordi-wall tools                            # перечень вызовов, число и отпечатки (ими судит приёмка)
gordi-wall help [<вызов>]                   # справка: общая или по вызову (то же дают --help и -h)
```

## Справка

```
gordi-wall help                    # общая: режимы · версия и отпечатки договора · вызовы · форма run · исход → код выхода
gordi-wall help <вызов>            # по вызову: заголовок · описание · аргументы · варианты · служебные записи · пример
gordi-wall --help | -h             # то же, что help (раньше служба поднималась и ждала ввода)
gordi-wall run <вызов> --help      # справка по вызову; тело инструмента НЕ запускается
```

Справке нужен только файл договора: манифест контуров она не читает (как и `tools`), контур не звать. Всё в ней строится
из договора: имена вызовов, заголовки, описания, аргументы (флаг `--имя-через-дефис`, тип, обязателен или нет, перечень
значений), строки вариантов (те же, что печатает `tools`, их строит `Contract.VariantLines`), служебные записи. Имя
аргумента выбора контура в форме вызова — тоже из договора. Добавили вызов или переименовали аргумент в договоре — справка
меняется без пересборки. В коде службы два места, которые не из договора: перечень режимов (его берут справка и отказ
«режима нет») и таблица «исход → код выхода» (её берут режим `run` и справка). Незнакомый вызов в справке — отказ в поток
ошибок с перечнем всех вызовов договора, код 4, стандартный вывод пуст. Справки у MCP нет: её роль играет `tools/list`.

## Ответ одним документом JSON: флаг `--json`

Режим `run` с флагом `--json` вместо текста печатает в стандартный вывод ОДИН документ JSON: ровно тот структурный ответ,
который служба MCP кладёт в `structuredContent` (общие поля любого вызова и необязательное поле `details`). Строит его одно
место в коде (`Program.StructuredOf`), поэтому расхождения между CLI и MCP нет. Код выхода прежний, по исходу; предупреждение
«вызов идёт мимо службы» остаётся в потоке ошибок. Флаг действует для любого вызова и описан в общей справке (раздел
«флаги режима run» берётся из того же места кода, что и перечень режимов). В других режимах флаг — отказ с причиной.
Имя занято: если договор объявляет аргумент с именем `json` (общий или вызова), служба в режимах `run` и `serve` отказывает
при запуске (код 4) и называет, где аргумент объявлен: флаг не должен молча заслонять аргумент.

Режим `run` существует как запас на случай «служба не поднялась». Он **всегда** печатает
в поток ошибок, что идёт мимо службы, и **всегда** отказывает пишущим вызовам: иначе обход
стены стал бы обычной дорогой и стена перестала бы что-либо значить.

## Исходы и коды выхода режима `run`

| исход | код выхода `run` | смысл |
|---|---|---|
| `passed` «прошло» | 0 | вызов исполнен, ответ полон |
| `mismatch` «расхождение» | 1 | исполнен, результат не совпал с ожидаемым состоянием |
| `not_started` «не запустилось» | 2 | тело не начало работу (интерпретатор не открыл файл, тела нет на месте, процесс не стартовал) |
| `cannot_verify` «не смог проверить» | 3 | служба не получила ответа тела по предмету: обрыв по времени, не удалось сохранить части длинного ответа, утерян итог частей |
| `refused` «отказ» | 4 | вызов отвергнут договором до исполнения (нет обязательного аргумента, неизвестный контур, лишний аргумент, чужая метка продолжения, запись в режиме только-чтение) |
| `partial` «частично» | 5 | тело отработало, но ответ отдан НЕ целиком: есть продолжение |
| `tool_failed` «тело отказало» | 6 | тело запустилось и кончилось ненулевым кодом: определённый отказ по его правилам (нет такой роли, неверный ключ подтверждения) или сбой внутри; служба ответ тела получила и отдаёт как есть: причина — в `error`, код тела — в `child_exit`. Причина — ОДНА строка тела: последняя, что начинается с признака ошибки (`ERR`, 🔴, ⛔, ❌, `ОТКАЗ`), а без признака — последняя непустая. Последняя — потому что причину выхода тело говорит последней, а предупреждения с тем же признаком печатает раньше. Признак-слово (`ERR`, `ОТКАЗ`) считается только целым словом: сводка `ERRORS: 0` признаком не будет. ⚠️ Граница выбора: если тело после причины печатает ещё одну строку с признаком, причиной станет она. ⚠️ Граница: ответ «не найдено» (код 1 у `owner_words_find`) тоже приходит этим исходом — это определённый ответ тела, а не поломка инструмента |

«Не запустилось» выбирается не подстрокой: нужен код выхода 2, пустой stdout и первая непустая строка потока
ошибок вида `…python…: can't open file …`. Фраза «No such file or directory» в выводе отработавшего тела
исходом «не запустилось» не является.

## Длинный вывод — частями, а не обрезкой

Вывод тела (только stdout) длиннее предела `max_output_chars` делится на части по границам строк
(строка длиннее предела режется по пределу). Первая часть отдаётся сразу, весь ответ ложится на диск
в `<временная папка пользователя>/gordi-wall-spool`, файл на ответ, имя — случайный id; срок хранения 2 часа,
просроченные свои файлы стена убирает при каждом обращении к каталогу.

- Поля ответа: `part` (номер с 1), `parts` (всего), `next_part` (метка продолжения или `null`), `final_outcome`.
  У ответа не по частям `part=1`, `parts=1`, `next_part=null`.
- Все части, кроме последней, имеют исход `partial`; в них `final_outcome` называет исход тела, чтобы не ждать конца,
  узнавая об отказе. Последняя часть несёт настоящий исход тела.
- Продолжение — общий необязательный аргумент `next_part` (нового вызова в договоре нет). Вызов с `next_part` тело НЕ
  запускает: отдаёт следующую часть сохранённого ответа. Метка привязана к вызову и контуру; чужая, неизвестная или
  просроченная — исход `refused`. Повторное чтение той же части разрешено. Остальные аргументы вызова при этом не нужны.
- Шапка ответа печатает «часть N из M» и точную форму следующего вызова для обоих режимов:
  `gordi-wall run <вызов> --contour <имя> --next-part <метка>`.
- Для ленты это важно: у `feed_read` вторая половина ключа подтверждения стоит в ПОСЛЕДНЕЙ части — дочитай до части без `next_part`.
- Поле `truncated` теперь означает только настоящее отсечение (предел времени; предупреждения тела длиннее предела).
  При выдаче частями `truncated=false`: ничего не отрезано.

## Предупреждения тела — отдельным полем

Поток ошибок тела (stderr) не приклеивается к тексту: он идёт полем `warnings` (пусто, если нет), а `ForRole()` печатает
его блоком ПЕРЕД текстом. При выдаче частями предупреждения целиком в первой части и повторены в последней.
Предупреждения длиннее предела — начало и конец с строкой «вырезано N знаков», `truncated=true` и причина:
это единственное место, где стена вправе отсечь. В `structuredContent` теперь есть и поле `text` (часть ответа без шапки).

## Незнакомый аргумент — отказ

Любой аргумент вызова, которого нет ни среди общих аргументов договора, ни среди аргументов самого вызова, даёт исход
`refused`: в причине названы лишний аргумент и перечень объявленных, тело не запускается. Проверка стоит в одном месте
(`ToolRunner.CallAsync`) и действует и в службе, и в режиме `run` (прежнее предупреждение режима `run` заменено отказом).
Опечатка вроде `limt` вместо `limit` иначе давала бы ответ на другой вопрос и выглядела как «прошло». Общий аргумент
`next_part` объявлен в договоре, поэтому отказа не вызывает. В `inputSchema` каждого вызова стоит
`additionalProperties: false`.

`contour_info` называет commit, из которого собрана стена (40 знаков; поле `judge.service_build_commit`), а в его источнике — признак

поле `judge.service_build_commit` отвечает «нечем проверить» с причиной «commit НЕИЗВЕСТЕН — собрано не из git». Сбой git сборку не роняет.

## Служебные записи читающих вызовов

Вызов с `mode: read` данных контура не меняет, но тела читающих вызовов пишут служебные таблицы: показанные подсказки
(`hint_seen`), выдачу ключа подтверждения (`read_batches`), счёт нового с прошлого чтения (`sync_backoff`),
а отбор `to_me` чтения ленты — что тела записок показаны (`cursor_segments`; отметку прочитанного это не двигает). Вызов
поэтому НЕ объявлен пишущим (режим `run` всегда только-чтение, и лента стала бы недоступна): договор называет служебные
таблицы явно полем вызова `service_writes`, а шапка договора определяет: «mode=read — данных контура не меняет;
служебные таблицы — только перечисленные в service_writes». Перечень виден в режиме `tools`, в описании вызова
для ролей и в файле договора. Приёмка (случай К8) сверяет его с замером: сводка по ВСЕМ таблицам базы до и после
каждого читающего вызова на своей копии базы стенда.

### Варианты вызова

Один вызов может нести несколько тел. Вместо одного `exec` у вызова три поля:

- `variant_by` — имя аргумента вызова, значением которого выбирается вариант (у него обязан быть `enum`);
- `variants` — объект «значение → вариант»; у варианта своё `title`, свой список `requires` (аргументы, обязательные именно
  в нём) и свой `exec`;
- `default_variant` — вариант по умолчанию, только у читающего вызова. У пишущего его быть не может: действие называется явно,
  и аргумент выбора (`action`) обязателен.

`required: true` на уровне вызова значит «обязателен в КАЖДОМ варианте». Всё прочее обязательное — в `requires` варианта.

Исполнение (порядок проверок в `ToolRunner.CallAsync` прежний; новое встаёт после ветки `next_part` и до проверки обязательных
аргументов): вариант = значение аргумента выбора или `default_variant`; значение вне перечня — прежний отказ по `enum`;
аргумент, переданный в вызове и НЕ относящийся к выбранному варианту, — отказ ДО запуска тела (текст называет аргумент,
выбранный вариант и варианты, к которым аргумент относится); не передан аргумент из `requires` — отказ ДО запуска тела
(текст называет вариант и аргумент). Исход `refused` («отказ») — не «тело отказало»: решает договор, а не тело. «Аргумент относится
к варианту» значит: он упомянут в `exec.args` или `exec.env` этого варианта. Исход читается из `mismatch_when` ВЫБРАННОГО варианта.

Справка `gordi-wall tools` и описание вызова в схеме MCP печатают по строке на вариант: «вариант view=edit: обязательны role, section;
можно … · название». Строки строятся из договора кодом, руками не пишутся. Отпечаток перечня вызовов (`ToolsFingerprint`)
считает и аргумент выбора с ключами вариантов: снятый вариант меняет отпечаток.

Разбор договора при загрузке отвергает (служба не поднимается, причина названа вызовом и аргументом): вызов без `exec` и без
`variant_by`/`variants`, а равно с обоими; `variant_by`, который не называет объявленный аргумент с `enum`; перечень значений,
не равный набору вариантов; `default_variant` вне перечня или у пишущего вызова; вызов без `default_variant`, у которого аргумент
выбора не обязателен; `exec.args`, `requires` или `exec.env`, ссылающиеся на необъявленный аргумент; `requires`, называющий аргумент, которого тело ЭТОГО варианта не использует (нет ни в его `exec.args`, ни в его `exec.env`): вариант стал бы невызываемым; аргумент вызова, не относящийся
ни к одному варианту; `required: true` у аргумента, который относится не ко всем вариантам; имя переменной среды не по образцу
`^MEZO_[A-Z0-9_]+$` (договор не вправе подменять телу `PATH`, `PYTHONPATH` и прочее чужое).

Правило о ВИДЕ значений: `requires` — массив строк (не массив или элемент не строка — договор не загружается); в перечнях строк
(`enum`, `service_writes`, `exec.pre`, `exec.sub`, `exec.mismatch_when`, `requires`) и в значениях `exec.env` любой элемент,
не являющийся строкой (число, `null`, объект), — отказ загрузки кодом 4 с названием места, а не падение службы с трассировкой.
Любой из этих отказов кончается кодом 4 и текстом «договор не читается» с названием места.

### Передача аргумента в среду тела: `exec.env`

У любого `exec` может быть `env` — объект «имя переменной → имя аргумента вызова». Значение аргумента, переданное в вызове,
становится переменной среды тела. Нужно одному месту: `memory-records.py --compact` берёт «чья рука» из `MEZO_ROLE` НАМЕРЕННО
(не из флага), а служба стирает все `MEZO_*` у тела. Порядок такой: сначала стираются все `MEZO_*` среды службы, затем ставятся
переменные из `env` выбранного `exec` (только при непустом значении аргумента). Среда самой службы к телу по-прежнему
не протекает: служба, поднятая с `MEZO_ROLE=EVIL`, телу его не передаёт. В варианте `compact` вызова `memory_write` обязателен
`actor`, он уходит в `MEZO_ROLE`; правило тела «роль сжимает СВОЮ память» остаётся в силе. Аргумента порога у `compact` нет
и быть не должно: порог читает само тело из своих правил.

### Границы новых вызовов — словами

- **Схема MCP не выражает «обязателен в варианте».** В `required` схемы вызова стоит только обязательное на уровне вызова;
  что обязательно в выбранном варианте, говорит отказ службы и строки вариантов в описании вызова.
- **`owner_words_add` зовёт искатель, который читает записи разговоров.** Искатель идёт по записям всей машины и может не уложиться
  в предел времени (карточка 797). Тогда исход «не смог проверить», слово НЕ записано. Тело само сверяет дословность и без находки
  слово не записывает (исход «тело отказало», слово не записано).
- **Тело памяти приходит в самом вызове, и сверка часа файла через службу не срабатывает.** Критерий ③ карточки 524
  (сверка часа файла с часом записи) остаётся защитой прямого вызова `save-phoenix.py`; через `memory_write action=save` защитой
  служат номер прочитанной версии (`expect_version`) и исход «расхождение».
- **Запрос `memory_find`, начинающийся с дефиса, не проходит.** Замер на малой копии (режим `run`): запрос с дефисом в начале даёт исход
  «тело отказало», код тела 2, причина «the following arguments are required: query» — разбор аргументов тела принимает такое слово
  за ключ. Не чинится: тела инструментов правятся не здесь. Обход: начинать запрос с другого слова.
- Ответ «не найдено» у `memory_find` приходит исходом «тело отказало» (код тела 2): это определённый ответ тела, а не поломка.

## Что за стену НЕ уходит — и почему

- **Приёмки и замеры.** Стена не может судить себя: судья обязан стоять снаружи.
- **Сверка версии установки.** Отпечаток считается по СОДЕРЖИМОМУ файлов вне службы;
  служба лишь показывает, что записал установщик (`meta.template_commit`, `meta.template_files_sha`).
- **Разрушающее** (`force push`, `drop`, `delete`, `reset --hard`) — только живым словом владельца.
- **git.** Отправка и merge — не предмет стены.

## О версии тулинга

Манифест о ней **не судит**: её пишет установщик в таблицу `meta` хранилища контура. Блок `tooling` из файла-образца
манифеста убран (договор 2.1.0, карточка 816); значения этого блока служба не читает и не печатает. Остался в чьём-то файле —
ответ называет это строкой предупреждения (`details.notes`, она же в тексте). Общее поле ответа `tooling_version` берётся
только из хранилища; нечем взять — пустая строка. Оно несёт строку `meta.template_commit` как есть, а поле
`manifest.tooling.version` строже: заполнено, только когда запись установки принята целиком. При повреждённой записи общее поле
может нести commit, а поле манифеста — «нечем проверить» с причиной: источник у обоих один, строгость разная.

## `contour_info`: поля манифеста и блок «кто меня судит»

Вызов отвечает всегда (исход «прошло», даже когда за службой ничего не работает) и несёт поля в `details`
(объявлены в договоре: `answer_shape` — поле `details`, у вызова — перечень `answer_fields`). Каждое поле — объект
`{value, source, state, reason}`: значение (строка, число или `null`), источник словами, состояние `filled` «заполнено» либо
`cannot_verify` «нечем проверить». У `cannot_verify` значение `null` и причина непустая; у `filled` причина `null`. Пустая
строка под видом заполненного поля не выдаётся. Текст ответа строится из тех же объектов (строка поля: значение · источник · состояние),
сырой вывод `db-q.py` в текст не вставляется.

```
details.manifest.contour.id               имя контура из вызова (манифест контуров)
details.manifest.tooling.version          meta.template_commit (номера версии пакет не ведёт: версией служит commit)
details.manifest.tooling.source.package   meta.template_source
details.manifest.tooling.source.commit    meta.template_commit
details.manifest.tooling.hash             свёртка записи установки meta.template_files_sha; тела файлов служба не перечитывает
details.manifest.tooling.files            число файлов (пар) в записи установки
details.manifest.storage.path             поле storage манифеста контуров
details.manifest.installed.at             meta.template_recorded_at (час записи происхождения; обновление установленного его не двигает)
details.judge.service_build_commit        commit сборки службы
details.judge.contract_version            версия договора
details.judge.contract_fingerprint        отпечаток файла договора
details.judge.rules                       свёртка свода правил (действующие правила)
details.judge.rules_active                число правил со status='active'
details.judge.rules_revoked               число остальных правил
details.notes                             строки-предупреждения (не поле)
```

⚖️ **Свёртки** (приёмка считает их сама, независимо, на Python; формулы обязаны совпасть). Запись установки: пары «имя → отпечаток»
из JSON-значения `meta.template_files_sha`, по имени побайтно (UTF-8); текст `имя<TAB>отпечаток<LF>` на пару; sha256; первые 12 знаков в нижнем
регистре. Свод правил: строки таблицы `rules` со `status = 'active'` по `rule_key` побайтно; текст `rule_key<TAB>version<LF>`; sha256; первые
12 знаков; `rules_active` — число этих строк, `rules_revoked` — число остальных. ⚠️ Граница, названная и в источнике поля: правка
тела правила без смены номера редакции свёртку не меняет. Свёртка свода говорит об ИМЕНАХ и НОМЕРАХ редакций, не о телах.

Хранилище читается штатным читающим инструментом контура `db-q.py` (метод `AskStorage`), сам он не менялся. Запись установки
читается ОДНИМ значением, правила — запросом с явным большим `--limit`. Разбор вывода недоверчивый: число разобранных строк сверяется
с числом в строке-шапке; слова об обрезании, пустой ответ, неразбираемый JSON, ненулевой код — «нечем проверить» с причиной именно
этого случая (хранилище не ответило · записи установщика нет · запись не разбирается · прочитана не целиком), без догадок и без значений
из усечённого чтения. Запись установки принимается целиком: не прочитан или не разобран любой её кусок — «нечем проверить» у каждого
поля записи. Установленная у контура копия `db-q.py` может быть старше той, что в дереве: нет строки с числом строк — это тоже «нечем проверить».
