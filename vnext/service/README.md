# Стена контура gordi — служба вызовов поверх прежних инструментов

Этап **Э1** переделки тулинга (слово владельца 2026-11-15 01:17 UTC, чат PROTO;
план — `atlas.archs/.mezosync/goal-gordipack-vnext/00-README.md`, дизайн — `01-DESIGN.md`,
оценка предложения о выносе за стену — `02-MCP-EVALUATION.md`, критерий приёмки — карточка 779).

Стена **не переписывает** прежние инструменты. Она становится **единственным общим входом к ним**:
роль больше не зовёт файлы напрямую, а просит вызов по имени и получает ответ,
у которого исход назван словом из закрытого перечня, а усечение — отдельным признаком.

## Что это лечит

| Класс из разбора 121 незакрытой карточки | Чем лечит стена |
|---|---|
| договор вызова живёт в голове роли (24 карточки) | договор — ОДИН файл, из него и служба, и справка, и перечень |
| код выхода беднее исходов инструмента (21) | типизированный исход + отдельный признак усечения; код тела — справочно |
| чаты правят инструменты напрямую (13) | тела за стеной; роль их не зовёт и не правит |
| инструмент считает путь контура сам (10) | контур приходит **в вызове**, среда ребёнка чистится от `MEZO_*` |
| обрыв текста неотличим от конца (2) | длинный вывод выдаётся частями, а не режется; `truncated` — только для настоящего отсечения; молча обрезать нельзя |
| кодировки | ребёнок всегда в UTF-8 (`PYTHONUTF8`), длинный текст идёт файлом, а не аргументом |

## Три режима одной сборки

```
gordi-wall serve --contours <манифест>     # служба MCP по стандартному вводу-выводу (так её зовут роли)
gordi-wall run <вызов> --contour <имя> …   # однократный вызов МИМО службы, ТОЛЬКО чтение
gordi-wall tools                            # перечень вызовов, число и отпечатки (ими судит приёмка)
```

Режим `run` существует как запас на случай «служба не поднялась». Он **всегда** печатает
в поток ошибок, что идёт мимо службы, и **всегда** отказывает пишущим вызовам: иначе обход
стены стал бы обычной дорогой и стена перестала бы что-либо значить.

## Исходы и коды выхода режима `run`

| исход | код выхода `run` | смысл |
|---|---|---|
| `passed` «прошло» | 0 | вызов исполнен, ответ полон |
| `mismatch` «расхождение» | 1 | исполнен, результат не совпал с ожидаемым состоянием |
| `not_started` «не запустилось» | 2 | тело не начало работу (интерпретатор не открыл файл, тела нет на месте, процесс не стартовал) |
| `cannot_verify` «не смог проверить» | 3 | служба не получила ответа тела по предмету: обрыв по времени, не удалось сохранить части длинного ответа, утерян итог частей |
| `refused` «отказ» | 4 | вызов отвергнут договором до исполнения (нет обязательного аргумента, неизвестный контур, лишний аргумент, чужая метка продолжения, запись в режиме только-чтение) |
| `partial` «частично» | 5 | тело отработало, но ответ отдан НЕ целиком: есть продолжение |
| `tool_failed` «тело отказало» | 6 | тело запустилось и кончилось ненулевым кодом: определённый отказ по его правилам (нет такой роли, неверный ключ подтверждения) или сбой внутри; служба ответ тела получила и отдаёт как есть: причина — в `error`, код тела — в `child_exit` |

«Не запустилось» выбирается не подстрокой: нужен код выхода 2, пустой stdout и первая непустая строка потока
ошибок вида `…python…: can't open file …`. Фраза «No such file or directory» в выводе отработавшего тела
исходом «не запустилось» не является.

## Длинный вывод — частями, а не обрезкой

Вывод тела (только stdout) длиннее предела `max_output_chars` делится на части по границам строк
(строка длиннее предела режется по пределу). Первая часть отдаётся сразу, весь ответ ложится на диск
в `<временная папка пользователя>/gordi-wall-spool`, файл на ответ, имя — случайный id; срок хранения 2 часа,
просроченные свои файлы стена убирает при каждом обращении к каталогу.

- Поля ответа: `part` (номер с 1), `parts` (всего), `next_part` (метка продолжения или `null`), `final_outcome`.
  У ответа не по частям `part=1`, `parts=1`, `next_part=null`.
- Все части, кроме последней, имеют исход `partial`; в них `final_outcome` называет исход тела, чтобы не ждать конца,
  узнавая об отказе. Последняя часть несёт настоящий исход тела.
- Продолжение — общий необязательный аргумент `next_part` (нового вызова в договоре нет). Вызов с `next_part` тело НЕ
  запускает: отдаёт следующую часть сохранённого ответа. Метка привязана к вызову и контуру; чужая, неизвестная или
  просроченная — исход `refused`. Повторное чтение той же части разрешено. Остальные аргументы вызова при этом не нужны.
- Шапка ответа печатает «часть N из M» и точную форму следующего вызова для обоих режимов:
  `gordi-wall run <вызов> --contour <имя> --next-part <метка>`.
- Для ленты это важно: у `feed_read` вторая половина ключа подтверждения стоит в ПОСЛЕДНЕЙ части — дочитай до части без `next_part`.
- Поле `truncated` теперь означает только настоящее отсечение (предел времени; предупреждения тела длиннее предела).
  При выдаче частями `truncated=false`: ничего не отрезано.

## Предупреждения тела — отдельным полем

Поток ошибок тела (stderr) не приклеивается к тексту: он идёт полем `warnings` (пусто, если нет), а `ForRole()` печатает
его блоком ПЕРЕД текстом. При выдаче частями предупреждения целиком в первой части и повторены в последней.
Предупреждения длиннее предела — начало и конец с строкой «вырезано N знаков», `truncated=true` и причина:
это единственное место, где стена вправе отсечь. В `structuredContent` теперь есть и поле `text` (часть ответа без шапки).

## Незнакомый аргумент — отказ

Любой аргумент вызова, которого нет ни среди общих аргументов договора, ни среди аргументов самого вызова, даёт исход
`refused`: в причине названы лишний аргумент и перечень объявленных, тело не запускается. Проверка стоит в одном месте
(`ToolRunner.CallAsync`) и действует и в службе, и в режиме `run` (прежнее предупреждение режима `run` заменено отказом).
Опечатка вроде `limt` вместо `limit` иначе давала бы ответ на другой вопрос и выглядела как «прошло». Общий аргумент
`next_part` объявлен в договоре, поэтому отказа не вызывает. В `inputSchema` каждого вызова стоит
`additionalProperties: false`.

## Кто меня судит: commit сборки

`contour_info` печатает commit, из которого собрана стена (40 знаков), признак «в дереве были незакоммиченные правки»,
адрес исходника (адрес `origin` без учётных данных и путь `vnext/service/GordiWall`) и каталог сборки; в `serverInfo`
службы есть поле `build_commit` (`serverInfo.version` остаётся версией договора). Значения вшиваются при сборке целью
`GordiBuildStamp` в `GordiWall.csproj`: `git rev-parse HEAD`, `git status --porcelain` по каталогу службы,
`git remote get-url origin`. Сборка не из git (выгрузка `git archive`) берёт commit из файла `build-stamp.txt`:
git подставляет в него `$Format:%H$` по `export-subst` из `vnext/service/.gitattributes`. Нет ни git, ни подстановки —
`contour_info` пишет «commit сборки НЕИЗВЕСТЕН — собрано не из git». Сбой git сборку не роняет.

## Служебные записи читающих вызовов

Вызов с `mode: read` данных контура не меняет, но тела читающих вызовов пишут служебные таблицы: показанные подсказки
(`hint_seen`), выдачу ключа подтверждения (`read_batches`), счёт нового с прошлого чтения (`sync_backoff`),
а отбор `to_me` чтения ленты — что тела записок показаны (`cursor_segments`; отметку прочитанного это не двигает). Вызов
поэтому НЕ объявлен пишущим (режим `run` всегда только-чтение, и лента стала бы недоступна): договор называет служебные
таблицы явно полем вызова `service_writes`, а шапка договора определяет: «mode=read — данных контура не меняет;
служебные таблицы — только перечисленные в service_writes». Перечень виден в режиме `tools`, в описании вызова
для ролей и в файле договора. Приёмка (случай К8) сверяет его с замером: сводка по ВСЕМ таблицам базы до и после
каждого читающего вызова на своей копии базы стенда.

## Сборка и подъём

```
dotnet build vnext/service/GordiWall
```

Манифест контуров кладётся **у контура**, не в пакете: в нём местные пути.
Образец — `contour/gordi-contours.example.json`; боевой файл — `<контур>/.mezosync/gordi-contours.json`.

Регистрация службы в чате роли (пока НЕ установлена — установка требует слова владельца):

## Договор

`contract/gordi-contract.json` — единственный источник. В нём: закрытый перечень исходов,
форма ответа, обязательный у каждого вызова аргумент `contour`, необязательный `next_part` и 12 вызовов:

```
чтение  memory_read        память роли (раздел или вся)
запись  memory_save        раздел памяти с номером прочитанной версии
чтение  memory_read_for_edit  раздел ДЛЯ ПРАВКИ: тело и номер версии первой строкой
чтение  feed_read          лента координации (отметку прочитанного НЕ двигает)
запись  feed_ack           подтверждение прочтения по ключу
запись  feed_write         записка в ленту (адресаты списком, не повтором флага)
чтение  cards_list         перечень карточек роли
чтение  cards_show         одна карточка целиком
запись  cards_comment      комментарий к карточке
чтение  rules_get          правило свода по ключу или перечень ключей
чтение  owner_words_find   слово владельца по куску текста
чтение  contour_info       кто меня судит: контур, версия тулинга, отпечатки
```

⚖️ **Вызовов нарочно 12, а не 365.** Схемы вызовов входят в контекст КАЖДОГО ответа роли:
замер соседнего контура показал, как справка о 540 репозиториях тащится в каждый ответ.
Стена покрывает рабочий отрезок роли, а не весь тулинг.

## Что за стену НЕ уходит — и почему

- **Приёмки и замеры.** Стена не может судить себя: судья обязан стоять снаружи.
- **Сверка версии установки.** Отпечаток считается по СОДЕРЖИМОМУ файлов вне службы;
  служба лишь показывает, что записал установщик (`meta.template_commit`, `meta.template_files_sha`).
- **Разрушающее** (`force push`, `drop`, `delete`, `reset --hard`) — только живым словом владельца.
- **git.** Отправка и merge — не предмет стены.

## О версии тулинга

Манифест о ней **не судит**: её пишет установщик в таблицу `meta` хранилища контура.
`contour_info` отвечает двумя половинами — своей (есть всегда) и из хранилища (когда оно
отвечает). Если хранилище молчит, так и сказано: «нечем проверить», а не «всё совпадает».
