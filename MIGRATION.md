# Мягкий переход md → SQLite

Управляется правилом `md-to-sqlite-phased-cutover` (в таблице `rules`).
Принцип: переход **поэтапный и общий для ВСЕХ ролей** — ни одна роль не отключает
md в одиночку, ни одна дормант-роль не пропускается.

## Фазы (модель миграции — для команды, переходящей на этот шаблон)

### Фаза 0 — Подготовка ✅
Схема · правила · шаблоны ролей · viewer · `init-group` · COORD-промпт.

### Фаза 1 — Двойная запись
Роль при каждом тике: читает из md (как раньше) + **дополнительно** пишет в `mezosync.db`.
md остаётся источником правды. Ошибка скрипта → не блокируется, тег `DWERR`.

### Фаза 2 — Двойная запись у ВСЕХ ролей + верификация
Каждая роль при ребёрсе получает в phoenix/launcher инструкцию двойной записи.
COORD верифицирует по каждой роли: дублирует чисто, 0 DWERR, phoenix сохранён в БД.

### Фаза 3 — SQLite = primary
Чтение только из SQLite · md генерируется `export-markdown.py` (read-only для людей) ·
phoenix хранится в таблице `phoenix` (7 секций, читается `read-phoenix.py`).

### Фаза 4 — md отключены ✅ (эталонное конечное состояние)
`sync.*.md` больше не пишутся · заморожены надгробиями · человекочитаемый вид генерируется из БД.
🚨 **Аварийный выход обязан существовать и быть обратимым БЕЗ правки кода:** `write-message.py … --md`
+ ГРОМКИЙ зов координатора. Ровно этого не хватило при ожоге 12.07 (роль молча отрезана, DWERR пропущен).

## 🚦 Гейт продвижения фазы (кто и когда переключает)

Перейти **к фазе 3** можно ТОЛЬКО когда:
- [ ] ВСЕ роли (включая дормант — её будит владелец launcher-ом) хотя бы раз вошли в двойную запись;
- [ ] у каждой роли есть свежий phoenix-слепок в таблице `phoenix`;
- [ ] 0 открытых DWERR (`check-errors.py`) на протяжении ≥ N тиков;
- [ ] COORD/владелец **явно объявил** продвижение фазы для ВСЕХ (нота + слово владельца).

**Роль НИКОГДА не бросает md сама.** Пока хоть один пункт не закрыт — md обновляется как обычно.

## 🔁 Процедура для команды коллег (переход на новую версию шаблона / на md-off)

Старая команда, переходящая на новую версию шаблона, включается ступенчато:
1. **Сначала — двойная запись** (читает блок «ДВОЙНАЯ ЗАПИСЬ» в своём phoenix).
2. **Держит двойную запись,** пока COORD не подтвердит верификацию (фаза 2 для этой роли).
3. **Отказ от md — только после** объявления фазы 3 для ВСЕХ ролей (не раньше и не в одиночку).
4. **К фазе 4** — по слову владельца, когда весь контур подтвердил доступ к тулкиту ИЗ контейнера
   (урок 12.07) и аварийный `--md`-выход проверен.

Новые группы (`init-group.py`) стартуют сразу с двойной записи — правило `md-to-sqlite-phased-cutover`
уже в их `rules`. **Endpoint (Фаза 4) проверен на живом контуре** — переходить к нему не страшно.

## 🗄 История

- md-архивы (`coordination/archive/sync.*.<дата>.md`) — каноничный исторический пласт, человекочитаемый.
- Ранняя md-история, импортированная в SQLite, вынесена в отдельную таблицу `messages_history`
  (+ VIEW `messages_all` для сквозного поиска) — чтобы не ломать хронологию id основной ленты
  (ретро-импорт давал «11 июля» с id выше сегодняшнего; курсор прыгал через непрочитанное).
- SQLite `messages` наращивает историю вперёд. На Фазе 4 полнотекстовые ноты живут В БД (не в md).

## Что НЕ меняется

- Git-коммиты координационных файлов — COORD продолжает коммитить.
- Push — только по живому слову владельца.
- Таймерный механизм (ScheduleWakeup/cron) — в ведении хоста. ⚠️ Модель — **pull** (роль сама читает
  ленту по своему ритму + датчик новых нот), а НЕ постоянный heartbeat-таймер: правило `timers-always-on`
  ПРОТУХЛО, см. `rules/universal.sql` v2.
- Viewer (`viewer/index.html`) — открывается локально, drag-and-drop `.db`.
