## 2. Схема — два шага после 13.09

Оба идемпотентны, оба понимают `--dry-run`; порядок — перечень `scripts/schema_step_order.py`.
Ставятся ПОСЛЕ двух шагов 13.09 (`UPGRADE-v5-to-2026-09-07.md`, раздел 7.1).

```
python <КОНТУР>/.mezosync/scripts/migrations/20260915-foreign-rebirth-marks.py --dry-run
python <КОНТУР>/.mezosync/scripts/migrations/20260915-foreign-rebirth-marks.py
python <КОНТУР>/.mezosync/scripts/migrations/20260924-role-sessions-transcript-id.py --dry-run
python <КОНТУР>/.mezosync/scripts/migrations/20260924-role-sessions-transcript-id.py
```

- **`20260915-foreign-rebirth-marks`** (коммит f817d6e, 15.09 14:38). Заводит таблицу
  `role_rebirths_foreign` и в контуре, отличном от эталона, ПЕРЕНОСИТ (не удаляет) туда отметки
  пересоздания, засеянные шагом `20260905-phoenix-history-archive` до его правки 15.09. Различитель —
  автор и источник строки (`noted_by='tool:20260905-phoenix-history-archive'`, источник
  `transcript:…`), а не имя роли: поэтому находятся и строки, чьи роли вы переименовали. Холостой
  прогон печатает, сколько и по каким ролям перенёс бы (у контура, применившего шаг до 15.09,
  таких строк 18).
  Проверка: `SELECT role, at, source, moved_at, moved_by, reason FROM role_rebirths_foreign ORDER BY role, at;`
- **`20260924-role-sessions-transcript-id`** (коммит 5c67fd9, 24.09 09:57). Добавляет необязательную
  колонку `transcript_id` в `role_sessions` и `role_sessions_history`: имя файла записи разговора, по
  которому хук узнаёт роль. Это ДРУГОЕ значение, чем `session_id` (тот доставляет сообщения). Шаг
  ничего не заполняет — значение приходит само сверкой `signal-templates.py` с хранилищем сессий
  приложения. Требует шаг `20260913-role-sessions-session-id`.

После обоих: `SELECT * FROM schema_version` → `v6 · <ваше число шагов> · 4` (четыре шага после
отметки v6: два от 13.09 и эти два). Новой отметки версии нет.

### 4.2 Как взять — `rules-from-pack.py`
```
python <КОНТУР>/.mezosync/scripts/rules-from-pack.py                   список расхождений по состояниям
python <КОНТУР>/.mezosync/scripts/rules-from-pack.py --show <ключ>     текст пакета, ваш текст, приложение
rules-from-pack.py --record-base --actor <роль> --apply                впервые: опора там, где текст уже совпадает
rules-from-pack.py --adopt <ключи> --word "<кто разрешил · когда · где>" --actor <роль> --apply
rules-from-pack.py --merge <ключ> --file <сведённый текст> --word "..." --actor <роль> --apply
rules-from-pack.py --skip <ключ> --word "..." --apply                  отказ, запоминается по тексту пакета
rules-from-pack.py --annexes --actor <роль> --apply                    приложения ключам с совпавшим текстом
```
`--word` обязателен при любой записи: взять чужой текст — решение вашего владельца или координатора,
инструмент подлинность слова не проверяет и говорит об этом прямо. Правило, запертое владельцем,
требует слова именно владельца. Приложение `--adopt` кладёт тем же ходом; ваше приложение с другим
текстом не переписывается без `--annex-force`. В шапке каждого приложения сказано: номера записок
и имена ролей в нём — эталона, в вашей ленте под теми же номерами лежит другое.

### 4.3 Правила ритма сверок — ваше решение
`sync-alarm-in-chat` и `sync-sleep-backoff`: в НОВОМ контуре рождаются снятыми (слово владельца
эталона 25.09 06:46:49 UTC «Новые — без будильников»). Текст в пакете прежний, и база правил пакета
статуса снятия не хранит — у вас сверка покажет «совпадает», а не «снято в пакете».
- **Снять:** `set-rule.py --key sync-alarm-in-chat --revoke --revoked-by owner --reason "…" --apply`,
  то же для `sync-sleep-backoff`.
- **Оставить:** впишите оба ключа в свой `skill-packages.json` — иначе пересобранный навык сверки
  их потеряет: сборщик образца вынул их из состава по умолчанию.
