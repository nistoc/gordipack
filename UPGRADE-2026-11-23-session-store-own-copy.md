## Зачем этот выпуск

```
беда ............ хранилище сессий приложения искалось в двух местах: переменная MEZO_SESSION_STORE или
                  стандартный каталог приложения в профиле (…/Roaming/Claude/claude-code-sessions).
                  У копии приложения со своим каталогом данных сессии лежат рядом с её файлами. У эталона
                  проверка ролей печатала «СВЕРИТЬ НЕЧЕМ … session_id 10 ролей НЕ ПРОВЕРЕНЫ» при живых
                  сессиях всех десяти; у onto — то же
вторая беда .... если по стандартному пути лежит хранилище ДРУГОЙ копии, сверка шла по чужому перечню:
                  у AIA «не найден» у 9 ролей из 9, а общий прогон проходил (проверка мягкая). Запись адреса
                  (signal-templates.py) по чужому перечню подбирала сессию по совпавшему имени — обратный ход
                  приёмки на прежнем пакете записал роли session_id чужого хранилища (случай S1, раздел 5)
что теперь ...... хранилище ищется рядом с копией приложения, из которой идёт чат (CLAUDE_CODE_EXECPATH),
                  и из кандидатов берётся то, где есть текущая сессия (CLAUDE_CODE_HOST_SESSION_ID).
                  Нет её и там — хранилище названо «вероятно, не наше», и по нему не судят
```

## 2. Что увидит контур

Проверка ролей в общем прогоне, своё хранилище найдено рядом с копией приложения:

```
✅ session_id живы у всех 10 ролей, у кого он записан (хранилище: <каталог данных копии>\claude-code-sessions —
   рядом с копией приложения (CLAUDE_CODE_EXECPATH); текущая сессия в нём есть)
```

Источник пути — одно из четырёх: «задан вызовом» · «переменная MEZO_SESSION_STORE» · «рядом с копией
приложения (CLAUDE_CODE_EXECPATH)» · «запасной стандартный путь (APPDATA)». Контрольное слово — «текущая
сессия в нём есть» или «своё ли оно — не проверено: переменная CLAUDE_CODE_HOST_SESSION_ID не задана».
Кандидатов больше одного — ещё заметка выбора («кандидатов 2, текущая сессия — в этом»).

⚠️ Хранилище, вероятно, чужое — общий прогон проверок проваливается:

```
🔴 ХРАНИЛИЩЕ СЕССИЙ, ВЕРОЯТНО, НЕ НАШЕ: текущей сессии «local_…» в нём нет — session_id N ролей по нему НЕ судятся
   (хранилище: … — <источник>)
   👉 укажите своё хранилище переменной MEZO_SESSION_STORE или проверьте, что CLAUDE_CODE_EXECPATH ведёт в
   каталог этой копии приложения
```

Не найден ни один из N ролей (N от 2) — перед строкой ИТОГ строка «НЕ НАЙДЕН НИ ОДИН из N — сперва проверьте
источник (…)»: чаще всего это не N мёртвых сессий, а не то хранилище.

Реестр адресов (`signal-templates.py --list`) сверяет адреса с найденным хранилищем: у эталона до выпуска
10 строк «⌛ СТАР» и «session_id сверить нечем», после — 10 строк «✅ сессия жива по session_id».

Из терминала вне приложения (переменные CLAUDE_CODE_HOST_SESSION_ID и CLAUDE_CODE_EXECPATH не заданы)
поведение прежнее: стандартный путь или переменная MEZO_SESSION_STORE, контрольное слово не судится.

## 3. Порядок установки

Общий порядок — раздел 3 `UPGRADE.md`: резервная копия, затем план и запись инструментов по merge commit
выпуска. Объявите установку в ленте до записи.

```
python <КОНТУР>/.mezosync/scripts/update-tools.py --rev <merge commit>             план
python <КОНТУР>/.mezosync/scripts/update-tools.py --rev <merge commit> --apply     запись

В плане ожидаемо «≠» у восьми файлов: в `.mezosync/scripts` — `mezo_sessions.py`, `mezo_stand.py`,
`write-message.py`; в `vnext-tools` — `mezo_sessions.py`, `mezo_stand.py`, `guard-role-sessions-live.py`,
`signal-templates.py`, `bite-signal-templates.py` (если они у вас там лежат). Новая приёмка

которые уже лежат. Её и набор ядра запускают из клона пакета.

После установки, из чата приложения (не из терминала — иначе контрольному слову нечего судить):

```

```

Ожидаемо — «✅ session_id живы у всех N ролей …» с источником и словами «текущая сессия в нём есть», код 0.
Строка «ВЕРОЯТНО, НЕ НАШЕ» — остановитесь и пришлите полный вывод.

Набор ядра, строка новой приёмки (из клона пакета на merge commit выпуска; `MEZO_CONTAINER` нужна, когда
клон лежит вне контура):

```

Ожидаемо после установки — «совпало 1 · разошлось 0 · не запустилось 0». ⚠️ ДО установки та же строка

установкой, а не правкой приёмки.

## 6. Чего выпуск НЕ делает

```
· второго носителя пути в базе контура (поле meta.session_store, письмо onto от 01.10) нет: с поиском рядом
  с копией приложения у обоих замеренных контуров (эталона и onto) он не нужен
· своё хранилище не угадывается, когда чат идёт не из приложения или CLAUDE_CODE_EXECPATH ведёт не в каталог
  копии: тогда работает только переменная MEZO_SESSION_STORE
· контрольное слово судит хранилище по ОДНОЙ сессии — текущей. Хранилище, где текущая сессия есть, а сессий
  ролей нет (роли в другой копии приложения), проверка честно назовёт «не найден» у каждой роли
· полного прогона набора ядра (81 приёмка) и полного pytest нет: прогнаны строки и файлы, которых касается
  выпуск; остальное судит CI ветки
· ⑰ bite-core-fixture.py не проходит, когда пакет лежит вне контура: случай зовёт bite-all.py без
  MEZO_CONTAINER. Так же и до выпуска; не исправлено
· свод правил, схема, пробуждение роли и общий прогон проверок (guard-all.py) не менялись: проверка ролей
  зовётся с --soft, как прежде, провал в мягком режиме даёт только исход «вероятно, не наше»
```
