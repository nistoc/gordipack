## Зачем этот выпуск

До этого выпуска правка инструмента могла прийти в пакет двумя путями: правкой в клоне пакета и
ПЕРЕНОСОМ из контура (`sync-to-template.py`, `guard-scripts-drift.py --to-template`). Перенос брал файл
из установленной копии и клал его в пакет — и мог затереть в пакете чужую, более новую правку старой
копией. Теперь путь один:

```
правка в клоне пакета → приёмка копии из клона → commit по именам файлов → push
→ установка в контур: update-tools.py --rev <commit> (план), затем --apply
```

Перенос «контур → пакет» снят: инструменты переноса не удалены, а отказывают словами и называют этот
путь (раздел 4.1). Тем же выпуском закрыты находки двух контуров, принимавших выпуск 05.10: ложная тревога
резервной копии и невидимые письма соседа (контур onto, разделы 4.2 и 4.8) и восемь мест контура AIA
(раздел 4.3).

## 2. Что значит «перенос снят» для вашего контура

Ваши инструменты в `.mezosync/scripts` — установленная КОПИЯ пакета. Расхождение копии с пакетом
показывает план `update-tools.py`; сверка пары `guard-scripts-drift.py` без ключа продолжает работать и
пишет словами, что не так:

| строка сверки | значит |
|---|---|
| «СОЗДАНО МИМО ПАКЕТА» | файл есть только у контура; путь — правка в клоне пакета |
| файл только в пакете | норма: пакет несёт приёмки и инструменты, которых ваши скрипты не зовут |
| расхождение | см. план `update-tools.py --rev <commit>` — он назовёт, что обновится и что правлено у вас |

Свою правку инструмента, которую хотите отдать в пакет, — заявкой пакета (`UPGRADE.md`, раздел 5) или
правкой в своём клоне пакета по пути выше; переноса из контура больше нет.

## 3. Резервная копия этого выпуска — в два приёма

До шага 1 у вас стоит ещё прежний `backup-db.py`. После сохранений памяти он сравнивает базу с прежней
выгрузкой, поднимает ложную тревогу «phoenix_records −N строк — удалять из неё никто не должен» (код 1) —
и тем же вызовом ЗАМЕНЯЕТ прежнюю выгрузку новой. После этого судить убыль новому инструменту уже не по
чему, а настоящую потерю от ложной тревоги не отличить.

Поэтому в разделе 5:
- **шаг 0** пишет копию в ОТДЕЛЬНЫЙ файл (`--out <ФАЙЛ>`, как разрешает `UPGRADE.md`, раздел 3, шаг 0):
  прежнему инструменту сравнивать не с чем («первый снимок»), а прежняя выгрузка на своём месте остаётся
  нетронутой;
- **шаг 4** — уже новый `backup-db.py`: сперва холостой прогон (без `--apply` он ничего не пишет и печатает
  тот же суд, что и с ним) сверяет базу именно с прежней выгрузкой; тревоги нет — запись.

Так убыль за всё время с прежней выгрузки судит новый инструмент (раздел 4.2), а у вас до самого конца
лежат обе копии.

## 4. Поведение, которое изменилось

### 4.1 Перенос «контур → пакет» (`2f1b7cb`)
`guard-scripts-drift.py --to-template` (в том числе голый ключ без имён файлов), `sync-to-template.py` и
`sync-vnext-pair.py` при любом вызове печатают:

```
⛔ --to-template СНЯТ (этап Э4, карточка #678): переноса «контур → пакет» больше нет.
   Ничего не перенесено и ничего не сверено.
   Пакет — единственный источник инструментов. Путь правки (правило fix-delivered-to-pack-remote):
     1. правка в клоне пакета (каталоги scripts/ или vnext/prototype/)
     2. приёмка копии из клона → commit по именам файлов → push
     3. установка в контур: python <КОНТУР>/.mezosync/scripts/update-tools.py --rev <commit> (план), затем --apply
   Расхождение контура с пакетом показывает план update-tools.py.
```

и выходят кодом 2. Ни контур, ни пакет при этом не меняются. Инструменты оставлены, а не удалены:
их вызов живёт в памяти ролей и в скриптах, и отказ называет новый путь там, где его ищут.

### 4.2 Резервная копия (`12a5d45`)
Пересборка записей памяти при каждом сохранении раздела (`save-phoenix.py`) штатно удаляет записи, чьих
тел в разделе больше нет. Прежний `backup-db.py` такую убыль не отличал от потери: «🔴 СТРОКИ ПРОПАЛИ БЕЗ
ЗАКОННОЙ ПРИЧИНЫ … phoenix_records −N строк — удалять из неё никто не должен», код 1. Новый судит по
самим пропавшим записям: номер, роль и раздел берутся из прежней выгрузки, и убыль законна, только если
каждый такой раздел сохранён не раньше часа прежней выгрузки. Иначе — тревога с поимённым перечнем
разделов. Пересборка записей рукой (`memory-records.py` без сохранения раздела) журнала не пишет — её
убыль остаётся тревогой. Переезды строк (шаг схемы `20260915-foreign-rebirth-marks`, свёртка ленты и её
обратный ход, возврат версий памяти) судятся по номерам: убыль таблицы законна, только если каждый
пропавший номер есть сейчас в таблице-цели. Почему в этом выпуске копия снимается в два приёма —
раздел 3.

### 4.3 Находки контура AIA при приёмке выпуска 05.10 (`c4221fa`)

- **④-2** `guard-printed-forms.py`: читает память ролей полным видом (`read-phoenix.py --full`) и не ставит

- **④-6** `mezo_paths.py`: поиск файла путей останавливается на первом каталоге с `.mezosync` — выше

- **④-8** `update-tools.py`: файл, совпадающий с пакетом, но со старым или пустым отпечатком установки,

### 4.4 Обновление и сборка (`3e4e73b`, `ed63627`)
- **Шаг схемы не звено.** Имя файла из `scripts/migrations/` больше не считается звеном, которое надо
  положить в `scripts/`. Плоскую копию `scripts/20260907-phoenix-records-fts.py` (дубль шага схемы, на
  который ссылается `find-phoenix.py`) не кладут ни обновление, ни свежая сборка. ⚠️ Копию, положенную
  прежней сборкой, обновление НЕ убирает (`update-tools.py` ничего не удаляет): она остаётся и вреда не
  несёт — это тот же текст, что `scripts/migrations/20260907-phoenix-records-fts.py`, и шаг на уже
  сведённой базе отвечает «уже сведено». Убирать ли её — решение вашего владельца.
- **Отпечатки шагов схемы.** `--apply`, `--record-only` и свежая сборка снимают отпечатки
  `migrations/*.py` ключом `migrations/<имя>` — набор ключей после всех трёх один.
- **Второй каталог установки** — необязательный ключ `prototype_install_dir` файла путей
  (`.mezosync/local/paths.json`) для файлов `vnext/prototype/*.py`. Ключа нет — прежнее поведение. Есть —
  файлы, уже лежащие во втором каталоге, сравниваются и ставятся там (те же знаки плана, путь в истории
  пакета — `vnext/prototype/<имя>`), отпечатки — с приставкой `prototype-dir::/`, план называет каталог
  каждого файла («→ скрипты» / «→ второй каталог»). Ставятся только `.py`, ничего не удаляется. Сведение
  (`--merge`) для файлов второго каталога не работает (раздел 7).

### 4.5 Перехватчик pre-commit в пакете (`46f15a1`) — только для тех, кто правит пакет
Проверку литералов контура-эталона (`vnext/tools/guard-donor-literals.py`) прежде звал только перенос.
Теперь её зовёт git перед каждым commit в клоне пакета — после одной команды в этом клоне:

```
git -C <КЛОН ПАКЕТА> config core.hooksPath .githooks
```

При находке commit отменяется с перечнем находок и командой просмотра; сбой самой проверки — тоже отказ.
Граница: перехватчик читает РАБОЧЕЕ ДЕРЕВО, а не индекс; эту щель закрывает проверка сделанного commit
(`guard-donor-literals.py --commit HEAD`). На ваш контур перехватчик не влияет.

### 4.8 Мост соседей (`546bf03`)
Обход папок моста знал одно устройство — `<контейнер>/<репозиторий>/.mezosync/bridges/<папка>`. Теперь
и второе — `<контейнер>/bridges/<папка>` (так раскладывает сборка `init-group.py`). Сосед папки второго
устройства берётся из таблицы связей `cross_links`, а не из имени папки. Строка о мосте при чтении ленты
кончается «(соседи в обходе: …)» или «(соседей в cross_links нет — …)». Проверка «вопросы соседей без
ответа» общего прогона берёт тот же перечень устройств.

Завести соседа, не открывая его базу (правило `no-scan-external-contours`), — если ваш владелец решил
связать контуры:

```
python <КОНТУР>/.mezosync/scripts/bridge-groups.py --source-db <КОНТУР>/.mezosync/mezosync.db --target-db <КОНТУР СОСЕДА>/.mezosync/mezosync.db --target-group <ИМЯ ГРУППЫ СОСЕДА> --description "<зачем связь>"
```

С `--target-group` база соседа не открывается — нужен только существующий каталог его контейнера; вместе
с `--bidirectional` — отказ. Отказы «❌» выходят кодом 2 (прежде 0 — вызывающий принимал отказ за связь).
